# 0041: Dormant finite recon projection

Status: additive projection only; execution unsupported.

## Decision

Reuse the existing human-signed plan digest, approval and consume-once execution
ordinal. Compile a single immutable two-tool journey; reserve its entire worst
case as one ordinal. A separate per-stage budget store, issuer or service is
unnecessary. Every original HTTP tuple must pass existing Strict scope rules.
DNS seeds, numeric resolvers, CIDRs and DNS bounds are separately explicit in the
signed plan, not inferred from an HTTP rule. Both artifact identities are checked.
The secondary context hash is appended to preserve positional Gate callers.

## Alternatives and limits

Running existing loose scanner adapters would not establish the required contract
or common-platform cancellation guarantees. Adding a new network enforcement
service or ledger would expand the approved architecture. Neither is adopted.
A pure projection and validator permits focused review without enabling execution.

No default capability, execution entry point, installation, background work or
credential enrollment is added. Gate rejects non-Gate profiles before side
effects. The model is limited to the exact Linux artifacts and constrained
options documented in this decision.
The 50M DNS term is a conservative source argument, not a saturated empirical
maximum. Windows behavior, actual enforcement, aggregate evidence handling and a
common cancellation platform require further acceptance before any activation.

Follow-up: finite recon uses the distinct `vardr.finite-recon-plan/1` schema
discriminator; the Gate JSON schema remains unchanged. See the compiler-enforced
[profile contract](../contracts/finite-recon-plan-v1.md). The existing ledger final
elapsed-time check also applies the earlier recon deadline before allocation or
consumption writes; it adds no store or execution capability.
