# v0.37.0 — Pinned, verified tool installs

**Date:** 2026-10-08

VardrRunner now installs the tools it runs, from pinned and hash-verified releases, into one
folder. Additive: tools already on `PATH` keep working and are reported as unverified.
Decision record: [ADR 0014](../docs/adr/0014-pinned-verified-tool-installs.md).

## Problem

VardrRunner executed whatever `httpx`, `nuclei`, `subfinder`, `dnsx`, or `naabu` the
operator's `PATH` resolved first, from wherever each had been installed. Nothing checked
that a binary was the one its author published, two runners could run different builds of
the same tool, and the tools were spread across folders an operator might not know about.

## Solution

```bash
vardrrunner tools install --all
vardrrunner tools list
```

- **One folder.** Binaries go to `~/.vardrmap/tools` with a receipt, `tools.lock.json`,
  beside the runner's config, runs, and journal. `tools purge` removes them all.
- **Pinned in the package.** `tool_manifest.json` pins each tool's version and, for Windows,
  Linux, and macOS on amd64 and arm64, the release archive URL and SHA-256. Because the
  hash ships with VardrRunner rather than being fetched from the release page, replacing a
  tool's release is not enough to get a modified binary installed.
- **Fail-closed install.** Download over HTTPS with a size cap; refuse the archive unless its
  SHA-256 matches the pin; extract only the expected binary, to a path VardrRunner chooses,
  bounded in size; require it to report the pinned version; move it into place in one
  rename; write the receipt. A failure at any step installs nothing and leaves no partial
  file.
- **Re-verified before use.** The runner re-hashes a managed binary the first time it
  resolves it in a process and whenever its size or modification time changes. A binary
  that no longer matches its receipt is not executed; the job fails with the reason.
- **Reported everywhere.** `doctor`, `status`, and `tools list` show each tool as managed
  and verified, failing verification, an unverified `PATH` copy, or missing.

Pinned versions: httpx 1.12.0, nuclei 3.11.1, subfinder 2.16.0, dnsx 1.3.1, naabu 2.6.1.
All 25 archives were hashed locally and matched each project's published checksums.

## Not managed

- **nmap** ships as an OS installer or package, not a single binary. `doctor` points to the
  OS install.
- **naabu's capture library** (libpcap on Linux/macOS, Npcap on Windows) is system software.
  `tools install naabu` and `doctor` warn when it is missing.
- **vardrgate** is installed from its own repository.
- **nuclei templates** are still managed by nuclei in its default directory; moving them
  into `~/.vardrmap/data` is a follow-up.

## Antivirus

Penetration-testing tools are routinely flagged. During development, Malwarebytes blocked
naabu on launch and quarantined it within seconds. The installer now recognises a binary
that disappears during its version check, installs nothing, and tells the operator that an
exclusion for `~/.vardrmap/tools` covers every managed tool if they trust them. `verify`
reports a tool quarantined after install as missing, with the same advice.

## Keeping pins honest

`scripts/pin_tools.py` is the only way pins change. It downloads every platform archive,
hashes it locally, requires a match with the tool's published checksums file, and checks
that the archive contains the binary before writing a pin. The `Tool pin drift` workflow
re-downloads every pinned archive weekly; a changed hash is an incident to investigate, not
a pin to refresh.

## Tests

973 tests (85 new), coverage 95.65%. New: `tests/test_toolchain.py` (hash mismatch, hostile
archives with extra or path-traversing entries, size lies in zip headers, exact version
matching, antivirus quarantine, tamper detection, receipt corruption, PATH fallback) and
`tests/test_tools_commands.py` (commands, runner resolution, `doctor`, the download
function). The suite still never touches the network or runs a real tool.
