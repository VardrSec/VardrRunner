# v0.44.0 — MCP phases 4/5: engagement reads and drafting

**Date:** 2026-10-09

The reads the Phase 3 prompts were missing, and the two drafting tools the roadmap asked
for. Decision record: [ADR 0015 § Amendment (v0.44.0)](../docs/adr/0015-mcp-server.md).
Builds on v0.42.0.

## New reads

| Tool | |
|---|---|
| `list_authorizations` | The engagement's authorization records and testing windows. The endpoint returns a bare array rather than a paginated envelope, so the page is taken in the adapter; the `offset`/`next_offset` contract the agent sees is the same as every other paged read. |
| `get_finding_activity` | One finding's history — revisions, remediation updates, completed retests. Paginated. |
| `list_deliverables` | The client-facing documents and their latest revision. Paginated. |
| `get_deliverable_revision` | One immutable revision, with its snapshot and markdown. |

These close the three contract gaps v0.42.0 shipped with. `brief` now reads the
authorization from `list_authorizations` instead of asking `get_engagement` for a field it
does not return, and keeps the per-finding write-ups (`list_reports`) distinct from the
client deliverables (`list_deliverables`). `retest` reads `get_finding_activity` to see
whether a retest already happened and what it concluded, rather than guessing from a status
that never meant "remediated".

## New drafting tools

- **`draft_test_cases`** — VardrGate authorization cases drafted from observed API
  operations (`endpoint_ids` from `list_api_endpoints`) or an OpenAPI 3.x document. Exactly
  one source; both or neither is a tool error. Marked read-only, because it is VardrMap's
  `test-cases/preview` and stores and queues nothing. Drafts arrive with placeholder path
  variables, no identity secrets and every access decision set to `skip`.
- **`draft_report`** — a per-finding write-up. A guarded write, like `create_finding`. It
  takes no `status` argument and always posts `draft`, so an agent cannot mark a write-up
  final or delivered.

## Two writes are assertions, not capabilities

VardrMap can save a reviewed test case and write a client deliverable revision. Neither has
a tool here, and the reason differs from the scope/auth/delete set, which is withheld to
bound what a compromised agent could do. **These are withheld because they are assertions
only a person can honestly make.**

**Saving a VardrGate test case** declares that a human reviewed it. That declaration is the
whole purpose of the step: the CLI spells it `--reviewed`, creates the review file
exclusively so a draft in progress is never overwritten, and refuses literal credentials —
all so a person has to look. An agent calling it would sign the operator's name to a review
it performed itself, and a saved case is what later drives real authorization tests against
a client's API.

**A deliverable revision** is immutable once written and is the document handed to the
client. An agent cannot unsay it, and the judgement on a deliverable is the operator's, not
a model's.

So the server drafts and reads in both areas and stops where a human has to commit. That is
a narrower surface than "expose the API", deliberately: the drafting and the reading are
most of the work, and the assertions stay where accountability already sits.

## An unreadable authorization list is unknown, not empty

`list_authorizations` raises rather than returning an empty inventory when VardrMap's
response is not the shape it expects. Reporting "unknown" as "none" would invite the agent
to tell the operator this engagement has no authorization on record — a serious claim to get
wrong in either direction on a pentest, and the same distinction `ffuf` draws between an
empty report and an unreadable one.

It also pages what it advertises. The first version emitted `next_offset` but took no
`offset` argument, so the page it pointed at was unreachable and the final record could not
be read at all.

## Tool surface

Reads: `list_engagements`, `get_engagement`, `list_scope`, `list_authorizations`,
`list_findings`, `get_finding_activity`, `list_assets`, `list_api_endpoints`, `list_recon`,
`list_jobs`, `get_job_events`, `list_reports`, `list_deliverables`,
`get_deliverable_revision`, `preview_job`, `draft_test_cases`.

Writes (the client asks the operator to approve each): `queue_job`, `queue_pipeline`,
`create_finding`, `draft_report`.

Still absent: anything that edits scope or authorization, stop-work, every delete,
member/API-key/settings management, saving a test case, and writing a deliverable.

## Tests

The exact tool surface, and a second forbidden set — `save_test_cases`, `create_deliverable`,
`create_deliverable_revision` and the other plausible names — asserted absent separately
from the scope/delete set so the two rationales do not blur. Read/write hints including
`draft_test_cases` as a read. Per tool: that `list_authorizations` caps a bare array and
tolerates an unexpected shape, that the paginated reads hit the right paths with the right
params, that `draft_test_cases` requires exactly one source and rejects a negative offset,
that `draft_report` always posts `status: "draft"` and exposes no `status` argument at all.
Prompt feasibility: `brief` names `list_authorizations` and both deliverable tools, `retest`
names `get_finding_activity` and checks for an earlier retest, `triage` can draft a write-up
but says it cannot finalise one.

1169 tests, 96.04% coverage.
