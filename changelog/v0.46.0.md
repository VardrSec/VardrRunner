# v0.46.0 — dalfox

**Date:** 2026-10-09

XSS scanning. Stage 2c of the tool sequence ADR 0014 anticipated, and the last of it.
**Pairs with VardrMap v0.41.0**, which adds the `dalfox` job type and its importer.

```bash
vardrrunner tools install dalfox
vardrrunner run dalfox --engagement <id> --from-recon --worker 10 --delay 100
```

| Option | |
|---|---|
| `--worker N` | 1–100, default 10. Concurrent workers **per target**. |
| `--delay MS` | 0–10000, default 0. Per worker. |
| `--mining/--no-mining` | Default on. Discover extra parameters to test. |

## Candidates, not findings

The report is uploaded as dalfox wrote it. Nothing in this runner re-grades a match, renames
a tier or decides what is confirmed — so dalfox's own tier (`V`/`R`/`A`/`I`), detection
method and confidence reach VardrMap intact, and VardrMap stores each match as a scan item
with `status: "new"`. The job summary says "XSS candidate(s)" for the same reason.

## Load is bounded in two places, because dalfox's concurrency multiplies

`--workers` is **per target**, and dalfox scans several targets at once. Left at its own
defaults (50 workers, 50 concurrent targets) a job could put roughly 2,500 requests in flight
at a client's host. So `--max-concurrent-targets` is pinned low and the operator's `--worker`
caps the per-target half: the ceiling is `worker × 5`, and `--delay` spaces requests out
further. Neither bound has a value that disables it.

`--include-all`, `--include-request` and `--include-response` are never passed. They attach
a client's request and response bodies to every finding, and that is not something to ship
to the backend as a side effect of a scan — the report still carries the payload and the
reflected evidence.

## dalfox's exit code is information, not just success or failure

dalfox exits `0` when the scan completed and found nothing, `1` when it completed and
reported findings, and `2` on an input, configuration or runtime error. **`0` and `1` are both
a completed scan.** The first version of this change treated every non-zero exit as a failure
— correct for every other tool here — and so **failed the job at exactly the moment dalfox
succeeded in finding XSS**, discarding the findings. Every unit test passed, because they
mock the subprocess. It was found by running the real binary.

The exit codes were then confirmed against dalfox 3.2.4 itself rather than taken from its
documentation: `0` on a page that reflects nothing, `1` on a reflected-XSS page, `2` on an
unreachable target. `_run_tool_status` returns the exit code and accepts a per-tool set of
success codes; `_run_tool` is unchanged for every other tool, and a test asserts exit `1`
still fails them.

### The outcome comes from the exit code and the report together

A report file existing proves nothing. For an unreachable target dalfox exits `2` **and
writes a perfectly valid, empty report**, which is indistinguishable from a clean scan if the
file is all you read.

| Exit | Report | Result |
|---|---|---|
| `0` | readable, no findings | success — a valid empty result |
| `1` | readable, with findings | success — uploaded as candidates |
| `2` / other | anything | **failure** |
| `0` or `1` | absent, empty, corrupt, wrong shape, or no `findings` array | **failure** — outcome unknown |
| `1` | readable, no findings | **failure** — findings claimed but never written down |
| `0` | readable, with findings | **failure** — the report contradicts the process |

The last two rows fail rather than guess which of the process and the report is right.
Entries in `findings` that are not objects are not counted, so garbage cannot turn a clean
scan into "findings reported".

If dalfox flags its own scan as `incomplete`, the job summary still says so: an incomplete
scan that found nothing is not evidence that there is nothing to find.

## Scheduled runs

A schedule queues an ordinary job, so `run dalfox` and `run ffuf` can recur. The load limits
(`--worker`/`--delay`, `--rate`) apply **per execution**, not across the engagement: each run
is a fresh process with its own full allowance, and nothing aggregates traffic across runs or
overlapping jobs. An hourly schedule means active scanning traffic every hour for as long as
it exists. The limits bound how hard one run pushes, not how often runs happen.

## The installer learned about nested archives

dalfox is a Rust project now, and its release layout differs from every tool pinned so far:

- **The binary is one directory inside the archive** (`dalfox-v3.2.4-linux-x86_64/dalfox`),
  where every other pinned tool puts it at the root. Rather than start searching archives at
  install time, an asset may now record a `member` — the path to the binary — and extraction
  stays "copy exactly this one named entry", which is what makes traversal names elsewhere in
  the archive inert. The path is validated to be relative, non-climbing, free of backslashes,
  and to end in the binary that entry installs, so it cannot redirect an install to some
  other file in the archive. `install()` now separates the path *inside* the archive from the
  name it installs *as*, which stays the bare binary name.
- **Its checksums are published per asset.** dalfox's `checksum.txt` covers only the source
  tarballs, so cross-checking against it would have attested the wrong files. `pin_tools.py`
  gained a `per-asset` mode that reads the sibling `<asset>.sha256`. The layout is not even
  consistent within one release — the Unix files are `sha256sum` output, the Windows one is
  `certutil -hashfile` prose — so the digest is located by shape, under two conditions: the
  file must contain exactly one distinct SHA-256, and it must name the asset it attests.
- **Asset names follow a different pattern**, so `Source` carries an `asset_template` rather
  than a hard-coded one.

The guarantee is unchanged: a pinned hash is cross-checked against a digest upstream itself
published, and the manifest — not the download site — is the trust anchor.

## Tests

`tests/test_dalfox.py` (65): config defaults, parsing and every rejection, including that the
concurrency ceiling cannot be opened up; argv — the `scan` subcommand (not the legacy
`dalfox file` form), `-i file`, `--format json`, `--workers`, `--delay`, `--silence`, that
`--max-concurrent-targets` is pinned, that `--skip-mining` appears only when mining is off,
and that no `--include-*` flag is ever passed. Then the four outcomes, each tested:

- a **valid empty result** (exit 0, readable report, no findings);
- **usable findings** (exit 1, readable report, findings uploaded untranslated);
- an **execution failure** (exit 2, *with a valid report on disk* — proving a file existing is
  not success), plus every other exit code (3, 126, 127, 255, a signal);
- **unreadable output** at both exit 0 and exit 1, in six forms: absent, empty, corrupt,
  wrong-shaped JSON, no `findings` key, `findings` not a list.

And the two disagreements (exit 1 with an empty report, exit 0 with findings), non-object
entries not being counted as findings, that exactly the two documented success codes are
passed through, that the relaxation is dalfox-only (every other tool still fails on exit 1),
and that the temp targets file is removed on every exit path. Then the install path: a
nested `member` is accepted, an absent one still means the root, seven member values that
could redirect an install are refused, and the shipped manifest pins a nested member for all
five platforms. `tests/test_cli.py` asserts the kwargs every option produces and that an
out-of-range `--worker`/`--delay` never reaches the command.

### Opt-in smoke test against the real binary

`tests/test_smoke_dalfox.py` runs the **actual pinned dalfox** through the real handler, which
is the only way to see what mocked tests cannot: the exit-code bug above went through 1165
green tests. Set `VARDRRUNNER_SMOKE=1`; without it the tests skip, so a default `pytest` never
launches a scanner. With it but no binary available, they skip and say how to install it.

It covers a vulnerable page (exit 1, findings parsed, no request/response bodies in the
report), a clean page (exit 0, valid empty report) and an unreachable target (exit 2 despite a
valid report). Safety is asserted, not just intended: the only target is a fixture server on
`127.0.0.1`, every request must come from loopback and stay under a ceiling, the load is two
workers with mining off, and every run has a 60-second timeout.

To prove it earns its place, the original behaviour was re-introduced as a mutation: the
vulnerable-page test fails with `dalfox exited with code 1`, exactly the bug.

1193 tests passed and 3 skipped by default; 95.81% coverage.
