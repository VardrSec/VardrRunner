# v0.36.0 — Target classification and local deny rules

**Date:** 2026-08-18

Completes roadmap §16, the one part of Phase 4 that shipped without its security
half. Additive; nothing blocks that did not block before.

## Problem

v0.35.0 delivered the shape half of target safety well — `validate_targets()`
rejects control characters, whitespace, embedded URL credentials, and targets
beginning with `-` (which would otherwise reach a tool as an argv option, e.g.
`--output=/etc/passwd`). What it did not do was ask **where** a target points.

There was no IP classification anywhere in the tree, which meant no
loopback warning, no link-local warning, no deny rules, and — the one that
matters — no cloud instance-metadata warning.

That gap is specific to how this runner is meant to be deployed. VardrRunner is
built to sit unattended on a VPS. Inside almost every cloud network,
`169.254.169.254` answers, and what it serves is instance credentials. A recon
pipeline whose wildcard expansion happens to include that address would have
pointed a scanner at the host's own IAM role with nothing said about it.

## Solution

`target_safety.py` classifies every resolved target as `public`, `private`,
`loopback`, `link_local`, `cloud_metadata` or `hostname`, and covers the
metadata endpoints across providers:

| Address | Provider |
|---|---|
| `169.254.169.254` | AWS, GCP, Azure, DigitalOcean, OpenStack |
| `169.254.169.253` / `169.254.169.123` | AWS VPC DNS / NTP |
| `169.254.170.2` | AWS ECS task metadata |
| `fd00:ec2::254` | AWS IPv6 |
| `100.100.100.200` | Alibaba Cloud |
| `192.0.0.192` | Oracle Cloud (legacy) |
| `metadata.google.internal`, `metadata`, `instance-data` | by name |

The more specific finding wins: `169.254.169.254` is link-local *and* metadata,
and it reports as metadata.

**Classification is lexical.** No DNS is performed. Resolving would mean a
network call per target on a path that must stay fast and work offline, and it
would open a TOCTOU gap against the tool's own resolution moments later — the
check would prove nothing about what actually gets scanned.

### Warnings never block

Findings are advisory, exactly like the backend's scope findings. The operator
owns where they aim; a runner that guesses wrong blocks legitimate work
mid-engagement. `private` is classified and counted but deliberately **not**
warned about — internal ranges are routine on an internal engagement, and
warning on them would train operators to ignore the output entirely.

### Deny rules are the one thing that blocks

Only when configured, and never by default:

```jsonc
// ~/.vardrmap/config.json
{ "deny_targets": ["cloud_metadata", "10.0.0.0/8"] }
```

```bash
VARDRRUNNER_DENY_TARGETS=cloud_metadata,loopback
```

A rule is a class name, a literal host, or a CIDR. A malformed rule matches
*nothing* rather than everything — a typo in config silently halting all work
would be worse than the rule not applying.

The override is `VARDRRUNNER_ALLOW_DENIED_TARGETS=1`, recorded as a
`deny_override` job event. An environment variable rather than a CLI flag,
deliberately: deny rules matter most on the daemon path, which has no command
line, and an env var in the service definition is visible to anyone auditing the
host.

### Statistics

Accepted, duplicates removed, blanks skipped, and a per-class breakdown, emitted
as a `target_stats` job event. Counts only — no target values — so it is safe to
put in the journal and in audit exports.

## Tests

866 tests (was 794), coverage 95.32%. `target_safety.py` at 98%, and
`commands/jobs.py` rose from 91% to 96%.

`tests/test_target_safety.py` covers twelve metadata spellings, loopback and
link-local across IPv4/IPv6, that a name is never guessed at, that malformed
input cannot raise, and — the invariant most easily broken by accident — that a
flagged target **still runs**. The job-path tests assert the same behaviours on
the unattended path: warn-and-continue, block when configured, continue with
survivors on a partial deny, and that an override leaves an audit event behind.

## Known limitations

- A hostname that *resolves* to a metadata address is not caught, by design (see
  the lexical-classification note above). The deny rule for `cloud_metadata`
  matches literals and the well-known names, not arbitrary CNAMEs.
- Deny rules apply to resolved targets, not to wildcard scope entries before
  expansion.
- IPv6 metadata coverage is limited to the AWS address; other providers had no
  stable documented equivalent at time of writing.
