# v0.25.0 — VardrGate API authorization test handler

Released 2026-07-08.

## Summary

VardrRunner becomes the execution plane for VardrGate. A new `vardrgate_api_test`
job type runs VardrGate API authorization tests locally and reports results back
through the standard job lifecycle, so the same poll → claim → run → upload →
done/fail flow that drives recon tools now also drives API security testing.

## Added

### `vardrgate_api_test` job handler

`VardrGateHandler` (registered as `vardrgate_api_test`) runs a VardrGate test:

- **Self-contained job.** Unlike recon handlers, there are no scope/recon targets
  to resolve — the `test_case` and `execution` settings travel inside the job
  config. `resolve_targets` surfaces the endpoint URL under test as the single
  "target" so the lifecycle proceeds and operators can see what runs.
- **Shells out to the binary.** `execute` writes the job envelope to a temp file
  and runs `vardrgate run --job <file> --out <result>`; the `vardrgate` binary is
  on the tool allowlist. The runner imports no VardrGate internals — the coupling
  is the CLI/JSON contract only.
- **Uploads to the job.** `upload` posts the sanitized result JSON to
  `POST /jobs/{id}/upload` and returns a one-line finding-count summary. VardrGate
  guarantees credential values never appear in the result.

### `VardrGateConfig`

Typed, validated config for the new job type: `test_case` (required object),
`execution` (optional object), and optional `policy_id`.

## Changed

### `ToolHandler.upload()` signature

`upload()` gained an optional `job_id: str = ""` parameter. Recon handlers ignore
it (they import to a program); the VardrGate handler uses it to attach the result
to the originating job. All existing call sites and handlers are backward
compatible via the default.

## Requirements

Running `vardrgate_api_test` jobs requires the `vardrgate` binary on PATH. It is
not needed for any other job type; `status` and `doctor` report its availability.
