# v0.29.0 — Telling a halt order from a lost race

**Date:** 2026-08-17

Phase 1a of the enterprise-grade roadmap. No CLI surface change; the happy path
behaves exactly as before.

## Problem

VardrMap has always evaluated every job against its authorization, testing
window and recorded scope. Findings ride back as a `warnings` array and the work
still runs — **stop-work is the one condition that refuses**, arriving as HTTP
403. VardrRunner read none of it. The entire claim path was this:

```python
try:
    client.claim_job(job_id)
except Exception as e:
    # 409 = another runner won the race; just move on without failing the job.
    con.print(f"[red]Could not claim job:[/red] {e}")
    return
```

Four very different situations produced identical output and identical
behaviour:

| Actually happened | What the operator saw |
|---|---|
| Stop-work engaged (403) | `Could not claim job: ...` |
| API key expired (401) | `Could not claim job: ...` |
| Backend down (500) | `Could not claim job: ...` |
| Another runner won (409) | `Could not claim job: ...` |

In every case the job stayed `pending`, so the daemon re-claimed it on the next
poll — and the next. An operator who had pulled the emergency brake watched a
runner that looked like it was retrying normally, every five seconds,
indefinitely. The `warnings` array was never read at all, so a job running
against an out-of-scope target or outside the agreed window said nothing.

## Solution

**One taxonomy, classified once.** `errors.py` defines `FailureCategory` and a
`RunnerError` hierarchy, with `classify_status()` as the single place a status
becomes a meaning. It is pure and stdlib-only — the bottom of the dependency
graph, so anything can raise a classified error without a circular import.

**403 is stop-work.** VardrMap answers cross-account access with 404 rather than
403 so object existence is never disclosed, which leaves 403 carrying exactly
one meaning. That assumption is load-bearing and recorded in ADR 0008.

**Advisory findings are shown before execution**, not after, so the operator
sees them while intervening is still possible:

```
⚠ Target is not in the recorded scope: a.com not in scope
⚠ Outside the agreed testing window
```

They do not block. That is the deliberate design (ADR 0001's amendment on the
backend side): scope is the operator's responsibility, and a platform that
guesses wrong blocks legitimate work mid-engagement.

**Stop-work suppression.** `execute_pending_jobs()` takes a
`blocked_engagements` set that the daemon owns for its lifetime. A halted
engagement is refused once, reported clearly, then skipped quietly. A restart
re-checks — so lifting stop-work needs no special command.

**Parsing is total.** `policy.py` owns every read of the `warnings` array, and no
input can make it raise: malformed, absent, wrong-typed and hostile payloads all
yield an empty tuple. Failing to *display* an advisory finding must never abort a
job the backend already permitted.

## Backward compatibility

- No command, flag or output format changed on the happy path.
- Generic `get`/`post`/`patch` still raise `requests.HTTPError`, so `doctor` and
  `status` — which legitimately care about raw status codes — are untouched.
- Classified errors are raised `from` the original `HTTPError`; the cause
  survives for triage.
- A catch-all remains around the claim as the daemon boundary. One unclassified
  failure logs a sanitized diagnostic and keeps the worker alive.

## Tests

540 tests (was 463), coverage 95.78%. `errors.py`, `policy.py` and
`commands/jobs.py` are each at 100%.

- `test_errors.py` — every status mapping, chaining, and the wire values of each
  `FailureCategory` asserted literally, since they are written to durable records
- `test_policy.py` — the documented shape, plus twelve hostile payloads that must
  not raise, ordering, immutability, and unknown reason codes shown rather than dropped
- `test_job_policy.py` — stop-work halts, emits `blocked`, runs no tool, is not
  marked failed, and suppresses its engagement on the next poll; a race stays
  non-fatal and does *not* suppress; auth/rate-limit/backend failures report their
  category; an unclassified error keeps the worker alive; warnings display before
  execution without blocking it

## Known limitations

- Stop-work suppression is in-memory. A daemon restart re-checks the backend —
  correct and deliberate now, but it means a long-lived halt is re-confirmed once
  per restart. Durable suppression arrives with the execution journal.
- Warnings are surfaced on **claim** only. The backend also returns them on
  `PATCH /jobs/{id}` when a job transitions to `running`, a path the runner does
  not use.
- `policy_warning` and `blocked` are new event kinds. If the backend rejects
  unknown kinds, they are dropped by the existing `_emit` warning path without
  affecting the job.

## Backend contract needed later

None for this phase — everything above works against VardrMap as it stands
today. Later phases will need an idempotent upload or job-state query for safe
reconciliation, and capability negotiation on the heartbeat response; both will
be specified as proposed contracts rather than implemented across repositories.
