# v0.31.0 — Credential storage fails closed

**Date:** 2026-08-17

Phase 1c of the enterprise-grade roadmap. **Contains one breaking change**, on a
single path: `login` with no OS keychain present.

## Problem

ADR 0004 chose the OS keychain as the default store, with a fallback: no keyring
backend meant the key went to `~/.vardrmap/config.json` in cleartext, with a
warning. That fallback was wrong for a reason the original decision did not
weigh.

**The machines least likely to have a keyring backend are exactly the machines
that run unattended.** A VPS. A container. A CI runner. The fallback optimised
for "the command succeeded" on precisely the hosts where a long-lived
unencrypted credential matters most — and the only signal was one yellow line in
provisioning output that nobody reads.

It also produced a documentation error that outlived several releases: the
README claimed logging in meant "no plaintext key on disk", and `docs/cli.md`
claimed the hidden prompt meant the key was "never written to disk in
cleartext". Both were corrected in v0.30.0 — but correcting the *description* of
a bad default is not fixing it.

## Solution

`login` refuses. With no keychain available it verifies the key against the
backend, **writes nothing**, and exits 1, naming three routes forward: the
`VARDRMAP_API_KEY` environment variable (nothing touches disk), installing a
keyring backend, or `--allow-plaintext-credentials` to accept cleartext
deliberately.

A keyring that is **present but fails to write** is treated exactly like an
absent one. Downgrading to cleartext because a keyring write errored would
reintroduce the behaviour being removed, at the moment it is least expected.

### Posture is now inspectable

`vardrrunner credentials` reports key source, whether it is encrypted at rest,
keychain availability, whether the config file holds cleartext, and file
permissions — never the key. `doctor` gained the same storage checks, and both
read from one module (`credentials.py`) so they cannot drift into describing the
same machine differently.

**The environment variable is not counted as "encrypted at rest."** It is not
written to disk by the runner, which is a genuine improvement, but any process
running as that user can read it and it usually ends up in a shell profile or a
systemd unit. Calling that encryption would repeat exactly the overstatement
this release exists to correct.

## Migration

| If you… | Do this |
|---|---|
| Log in on a desktop with a keychain | Nothing — unchanged |
| Use `VARDRMAP_API_KEY` already | Nothing — unchanged, and this is the recommended path |
| Run `vardrrunner login` on a headless box | Switch to the env vars, or add `--allow-plaintext-credentials` |
| Already have a cleartext key on disk | It keeps working; `vardrrunner credentials` will tell you it is not encrypted |

Nothing is persisted before the refusal, so a failed login cannot leave a
half-configured machine — rerunning after choosing a route is safe.

## Tests

605 tests (was 588), coverage 95.63%.

`tests/test_credentials_posture.py` covers the refusal path, the explicit
opt-in, the keychain-write-failure case, that the keychain path never writes the
key to the file, that the refusal message names the env var route and carries no
key, that `inspect()` survives a corrupt config file, and that neither the
status object's `repr` nor the command's output can contain a key.

## Known limitations

- `logout` is unchanged and still clears both stores.
- Existing cleartext keys are not migrated or deleted. Removing a key an
  operator may still depend on is not a change to make on their behalf;
  `credentials` reports the situation, and `login` moves it into a keychain when
  one appears.
- Config-file permissions are only meaningful on POSIX; on Windows the check
  reports "not enforced", as before.
