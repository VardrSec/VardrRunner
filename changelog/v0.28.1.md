# v0.28.1 — A safety cap that a minus sign could switch off

**Date:** 2026-08-17

Patch release. One security-relevant fix and one documentation correction, both reported
against v0.28.0 within hours of it reaching PyPI.

## `--max-targets -1` disabled the cap

v0.28.0 exposed `--max-targets` on the command line for the first time. Every guard that
consumes it is written the same way:

```python
if max_targets > 0 and len(targets) > max_targets:
```

`0` was the documented way to disable the cap, and that reads naturally from the condition.
What the condition also does — silently — is treat **every negative value** as "disabled".
`--max-targets -1` parsed cleanly, arrived in the command module as `-1`, and skipped the
check completely. A confirmed reproduction passed 10,000 targets through a guard the
operator had every reason to believe was active.

This matters more here than it would in most tools, because the thing on the other side of
the cap is nmap and nuclei pointed at someone's infrastructure. `-1` is also a widespread
convention for "unlimited", so an operator could plausibly type it *expecting* the cap to
lift — and be right, by accident, via a path nothing documented or tested.

The bug was reachable only from v0.28.0 onward. Before that the option did not exist, so
every CLI invocation used `MAX_TARGETS_DEFAULT` and negatives were unreachable in practice.

### Fix

Rejected at two layers, because they fail differently:

- **Parse time** — `min=0` on the Typer option for all six `run` commands and
  `pipeline run`. The operator gets click's range error and nothing executes.
- **Inside the guards** — a new `run.validate_max_targets()` raises on a negative, called
  from `_check_target_cap()` and from the top of `run_pipeline()`. This covers programmatic
  callers, and it covers `pipeline._run_stage()`, which does its own inline
  `max_targets > 0` test rather than going through `_check_target_cap()`.

Validating in `run_pipeline()` rather than per stage means the pipeline refuses before any
stage runs, instead of aborting midway with some tools already fired.

## The API key prompt does not prevent plaintext storage

`docs/cli.md` claimed that omitting `--key` and using the hidden prompt meant the key was
"never written to disk in cleartext", and the README said logging in leaves "no plaintext
key on disk". Both overstate what the prompt does.

Where the key is *stored* has nothing to do with how it was *supplied*. `login` tries the
OS keychain, and when no keyring backend is present it falls back to writing the key in
cleartext to `~/.vardrmap/config.json` — with a warning, but it writes it either way. On a
headless VPS or in a container, which is exactly where unattended runners live, that
fallback is the normal path rather than the exception.

The prompt protects one thing: shell history. That is worth doing, and it is all it does.
Both files now say so, and both point at `VARDRMAP_API_KEY` for machines without a
keychain, since the environment path writes nothing to disk.

## Tests

463 tests (was 450):

- `test_validate_max_targets_rejects_negative` — parametrized over `-1` and `-500`
- `test_validate_max_targets_accepts_zero_and_positive`
- `test_check_target_cap_rejects_negative_before_counting` — aborts even when the target
  count is trivially small, proving the check runs before the comparison
- `test_run_rejects_negative_max_targets` — parametrized across all five targeted `run`
  tools, asserting the command module is never reached
- `test_pipeline_rejects_negative_max_targets_at_parse_time`
- `test_pipeline_rejects_negative_max_targets` — the `run_pipeline()` layer directly

The lesson is recorded in `CLAUDE.md`: for an option that gates a safety check, test the
out-of-range values, not just the happy path.
