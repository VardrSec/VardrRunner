# v0.45.0 — MCP phase 6: methodology checklists

**Date:** 2026-10-09

Two versioned methodology checklists, served to the agent, with a hard line between what a
checklist suggests and what an engagement has evidenced. Decision record:
[ADR 0015 § Amendment (v0.45.0)](../docs/adr/0015-mcp-server.md). Builds on v0.44.0.

## What ships

| Methodology | Edition | Items |
|---|---|---|
| OWASP API Security Top 10 | 2023 | 10 risks (`API1:2023` … `API10:2023`) |
| OWASP Web Security Testing Guide | 4.2 | the 12 top-level categories (`4.1` … `4.12`) |

`methodologies.json` lives inside the package, like `tool_manifest.json`. `list_methodologies`
and `get_methodology` read it locally — **neither makes an API call**, which also means a
checklist cannot be influenced by anything a target says. Each methodology is pinned to an
exact edition and each item carries its own source URL, so a write-up can cite precisely what
it was assessed against: "OWASP API Security Top 10 (2023)" is checkable, "the OWASP Top 10"
is not.

The WSTG entry covers the twelve top-level categories, not the individual tests within them.
Test-level granularity can follow; the categories are what the fetched source confirmed.

## Coverage is not representable, on purpose

The schema **refuses** `status`, `covered`, `done` and `coverage` at load time, and a test
asserts each is rejected.

A tick-box per item is the obvious design and it is a trap. A checklist that can hold a tick
will get one as soon as a scanner runs, and "assessed against the OWASP API Security Top 10"
with ticks earned by a nuclei job is a false claim in a client deliverable. Wrong data in an
engagement's record is worse than no data — the same reasoning behind ffuf's
auto-calibration and its unreadable-report failure.

So an item carries what to look at, which job types relate, and `method` — **how it is
tested, not whether it has been**:

- **`tooling`** — a job type here can produce evidence bearing on the item, and evidence of a
  *candidate* at that. A nuclei match is not a confirmed finding.
- **`manual`** — no job type here can establish it; it is tested by hand. Business logic,
  authentication flows, session handling, sensitive business flows. A test asserts **both**
  shipped methodologies contain items of each kind, so the distinction cannot quietly become
  decorative. A `manual` item may still name a job type worth a look.

Whether this engagement covered an item is derived when asked, from its own jobs and
findings, cited by id — **and a recorded manual test counts**. Queueing scans will never
cover a `manual` item, but a hand-tested authentication issue written up as a finding with an
activity entry is evidenced, and belongs under "evidenced" with those ids.

The field was first named `evidence`, which invited reading "tested by hand" as
"unevidenced": the prompt routed every `manual` item to "requires manual testing" whatever
the record said. How a test is performed says nothing about whether it was performed. The
field is now `method`, the old name is refused at load so the conflation cannot creep back,
and the prompt sorts on the record.

## Scope is stated, not implied

Each methodology carries a `scope` field. The WSTG entry covers the guide's twelve top-level
categories by section number; OWASP additionally gives every test scenario a stable
identifier of the form `WSTG-<version>-<category>-<number>` (`WSTG-v42-INFO-02`), and a
category is not coverage of the scenarios beneath it. Scenario-level mapping is deferred, and
the prompt is told not to cite a scenario identifier it has not assessed.

## The `methodology` prompt

Reads the checklist and the engagement's record (`list_jobs`, `list_findings`,
`list_api_endpoints`, `list_recon`, `get_finding_activity`) and sorts every item under three
headings: **evidenced** (naming job or finding ids, whatever the method — no ids means it
does not belong there), **not evidenced, a job would help** (`method: tooling` with nothing
in the record yet, and which job would change that), and **not evidenced, needs hands-on
work** (`method: manual` with nothing in the record, so queueing scans will not move it).

It sorts on the record rather than the method, in both directions: a hand-tested item that
was written up is evidenced, and a `tooling` item is not evidenced merely because its
suggested job type exists — something must actually have run.

Three rules it is held to, because this output ends up in front of a client: a tool having
run is not coverage; a scanner match is a candidate, not a finding; and **no percentage or
score** — a methodology is not something you can be 70% through, and a number collapses the
first two rules. Counts per heading are fine. It is also told to say plainly that this is a
planning aid against a published methodology, not a certification of compliance.

## Validation earns its keep immediately

Every `suggests` entry must name a job type in the handler registry. That caught the
checklist suggesting `ffuf` for API9 and WSTG 4.1/4.2 while ffuf's handler was still on an
unmerged branch — a suggestion pointing at a tool this runner cannot run. Those three
suggestions are left out here and are a one-line follow-up once ffuf lands.

## Licensing

Only identifiers, official titles and source URLs are referenced from OWASP. The guides are
CC BY-SA 4.0 and these repositories are AGPL-3.0, so rather than reason about share-alike
interaction, **no OWASP prose ships**: the "what to look at" notes and the job-type
suggestions are this project's own, and each methodology carries an `attribution` field
naming the source and its licence. Shipping fuller WSTG test text would need that call made
deliberately.

## Tests

`tests/test_methodologies.py` (36) covers the shipped data — both editions pinned, item
counts, per-method counts summing to the total, every source an HTTPS URL, every methodology
crediting CC BY-SA, every suggested job type real, no item carrying coverage or the old
`evidence` field, both methodologies mixing methods, and the WSTG scope naming the deferred
scenario identifiers — then what the schema refuses: each coverage field, the old `evidence`
name, malformed documents, bad entries, bad items, duplicate ids, an unusable methodology id,
and that a manual item may still suggest.

`test_mcp_server.py` adds the two tools (local, no API call, edition echoed, scope stated,
paging, unknown id, negative offset) and the prompt's contract: the three headings, ids
required, no percentage, asks which methodology when none is given, that it sorts on the
record rather than the method in both directions, and that it does not cite an unassessed
WSTG scenario identifier.

1221 tests, 96.06% coverage.
