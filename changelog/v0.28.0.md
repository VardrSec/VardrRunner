# v0.28.0 — Two flags that lied, and the first PyPI release

**Date:** 2026-08-17

Minor release. One option becomes reachable, one dead command disappears. This is also the
first version published to PyPI, so it is the first release most people will install with
a single command — which is why it was worth cleaning the CLI surface first.

## Problem

Both defects were the same shape: the *implementation* changed and the *command-line
surface* did not.

**`--max-targets`.** v0.22.1 added a guardrail that aborts a run when the resolved target
count exceeds 500, so a broad wildcard scope cannot silently become a several-thousand-host
scan. The enforcement shipped correctly — `MAX_TARGETS_DEFAULT` in `commands/run.py`,
`_check_target_cap()` called by all six `run_*` functions, and an equivalent check per
stage in `commands/pipeline.py`. The option to *change* it never made it into `cli.py`. So
for six releases the cap was real but fixed: an operator who legitimately needed to scan
800 hosts was told to "pass `--max-targets 0` to disable", and that flag did not parse.

**`import ffuf`.** v0.21.1 removed `ffuf` from `SUPPORTED_TOOLS` because it has no handler
and the backend has no ffuf import type. The `@import_app.command("ffuf")` registration was
left behind, so the command kept appearing in `vardrrunner import --help` and every
invocation reached `import_file()` only to exit with "Unsupported tool: ffuf".

## Why the tests did not catch either

`tests/test_cli.py` exists to verify Typer wiring, and its assertions were of the form:

```python
with patch("vardrrunner.commands.run.run_httpx") as mock:
    invoke("run", "httpx", "--engagement", "p1", "--target", "https://a.com", "--yes")
mock.assert_called_once()
```

`assert_called_once()` is true whether or not `max_targets` reached the command module, so
the missing option was invisible. The ffuf test was worse: it mocked `import_file` and
asserted it was called with `"ffuf"` — which passed precisely *because* the mock replaced
the code that would have rejected it. The test encoded the bug as expected behaviour.

## Solution

- `--max-targets N` on `run httpx|subfinder|nuclei|nmap|dnsx|naabu` and on `pipeline run`,
  defaulting to `run.MAX_TARGETS_DEFAULT` and passed through to the existing checks. `0`
  disables the cap. Help text is shared via one `_MAX_TARGETS_HELP` constant so `run --help`
  and `pipeline run --help` cannot drift apart.
- The `import ffuf` command is deleted. `SUPPORTED_TOOLS` is unchanged — it was already
  correct.

## Tests

450 tests (was 439). New coverage asserts the wiring rather than the call:

- `test_run_max_targets_is_passed_through` — parametrized across httpx, nuclei, nmap, dnsx,
  naabu
- `test_run_subfinder_max_targets_is_passed_through`
- `test_run_max_targets_defaults_to_the_shared_cap`
- `test_run_max_targets_zero_disables_the_cap`
- `test_pipeline_run_max_targets_flag` and `..._defaults_to_the_shared_cap`
- `test_import_ffuf_is_not_a_command` — asserts a non-zero exit and that `import_file` is
  never reached, replacing the test that mocked the failure away
- `test_import_help_lists_only_supported_tools`

The lesson is recorded in `CLAUDE.md`: when adding a flag, assert the kwarg it produces.
