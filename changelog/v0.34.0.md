# v0.34.0 — Compatibility and local safety controls

Phase 4 bounds the work one small-team runner can accept while keeping deployment simple.

## Operator features

- Heartbeats advertise runner version, supported job schema versions, and capabilities.
  A backend may return minimum/maximum runner versions, required capabilities, and accepted
  schemas. Hard mismatches pause claims; heartbeat negotiation continues so recovery does
  not require a daemon restart.
- Queue limits default to 500 targets, 100 MiB per artifact, one concurrent job, and a
  512 MiB free-disk reserve. Environment variables can raise or lower these within guarded
  bounds, and `doctor` reports the effective values.
- Concurrency is opt-in up to eight workers. Work is partitioned by engagement, ensuring
  two jobs for the same engagement never execute at once.
- `vardrrunner update check` checks PyPI without installing anything and caches the result
  for 24 hours.

## Compatibility

Existing backends may ignore the additive heartbeat advertisement and return no
compatibility object; that is treated as legacy-compatible. Jobs with no `schema_version`
remain schema v1. Default concurrency is one, preserving prior execution order. No new
runtime dependency or backend migration is required.

Scope and testing-window findings remain advisory. Local shape and resource controls reject
unsafe or oversized input regardless of `--yes`, but do not reinterpret backend scope.
