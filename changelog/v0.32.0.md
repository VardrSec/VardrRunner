# v0.32.0 — Durable execution and audit

Phase 2 replaces best-effort in-memory lifecycle tracking with durable local evidence.

## What changed

- Every queue job is inserted into `~/.vardrmap/runner-journal.sqlite3` before claim.
- Lifecycle transitions, child PID, target count, policy warnings, failure taxonomy,
  artifact path/hash/size, and upload state are committed transactionally.
- Daemon and one-shot queue execution reconcile unfinished records before polling.
- Completed runs receive an atomic, sanitized `manifest.json`.
- `audit list`, `audit show`, and `audit export` expose local evidence without contacting
  VardrMap.

## Recovery policy

Recovery resumes only operations with a known-safe outcome. A complete artifact that was
never uploaded can be uploaded; a successful upload awaiting final status can be finalized.
If an upload request may have succeeded but its response was lost, VardrRunner does not
replay it because VardrMap currently supplies no idempotency key. The job is closed failed,
while the artifact and audit record remain available.

## Compatibility

No backend migration or new Python dependency is required. SQLite is part of Python's
standard library. Existing direct `run`, pipeline, import, and authentication commands are
unchanged; durable journaling applies to backend queue jobs (`jobs run` and the daemon).
