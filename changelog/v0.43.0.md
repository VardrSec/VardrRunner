# v0.43.0 — ffuf

**Date:** 2026-10-09

Active content discovery. Stage 2b of the tool sequence ADR 0014 anticipated.
**Pairs with VardrMap v0.40.0**, which makes `ffuf` a queueable job type.

## What it does

```bash
vardrrunner tools install ffuf
mkdir -p ~/.vardrmap/wordlists
cp /usr/share/seclists/Discovery/Web-Content/common.txt ~/.vardrmap/wordlists/common.txt
vardrrunner run ffuf --engagement <id> --from-recon --wordlist common --rate 25
```

ffuf fuzzes each target's **site root** for hidden paths and uploads the hits as recon.
Targets collapse to roots first (`https://a.test/login` and `https://a.test/admin` are one
root), so a recon table with twenty URLs on one host fuzzes that host once.

| Option | |
|---|---|
| `--wordlist <name>` | A name, not a path. Default `common`. |
| `--extensions .php,.bak` | Appended to each word. A bare `php` gains its dot. |
| `--match-codes 200,301,403` | Statuses to keep, or `all`. Default: ffuf's own. |
| `--rate N` | Requests per second, per target. 1–1000, default 50. |

## Wordlists are named, never pathed

A queued job sends a wordlist **name**; the runner resolves it against
`~/.vardrmap/wordlists` on the machine doing the scanning. A path, a traversal, a drive
letter — anything path-shaped — is refused.

This is the point of the design, not an inconvenience. If a job could supply a path, the
backend would be able to name any file the runner can read, and ffuf would read it and
replay its lines at a target: a file-disclosure primitive built out of two features that
are each individually reasonable. The name's shape (`[a-z0-9][a-z0-9_-]*`) admits no
separator, `FfufConfig` refuses anything else at parse time, and `runner.resolve_wordlist`
re-checks the resolved parent before the subprocess starts. A symlink *inside* the
directory is honoured — pointing `common.txt` at a SecLists file is the operator's own
decision on their own machine, and nothing the backend can influence.

No wordlists ship with VardrRunner; their licences and sizes are the operator's choice. A
missing or empty one fails the job with a message naming the file it expected.

## Load is capped, and calibration is not optional

ffuf is the only tool here that puts sustained load on a client's host, so:

- **`-rate` is always passed.** It has a modest default (50/s), a ceiling of 1000, and no
  value that disables it. ffuf's own default is unbounded threads.
- **`-ac` (auto-calibration) is always on.** A host that answers every path with `200`
  would otherwise import thousands of phantom endpoints into the shared recon store, which
  is worse than finding nothing — it is wrong data in an engagement's record.
- **A non-zero exit on any one target fails the job.** Skipping that host quietly would
  report coverage the engagement does not actually have.
- **An unreadable report fails the job too.** A valid report with an empty `results` array
  means ffuf found no matches and the job succeeds. A report that is absent, unreadable or
  not the shape ffuf writes means the outcome is *unknown*, which is a different result —
  treating the two the same would finish a broken run green while recording that this host
  has nothing on it. A single malformed entry inside an otherwise valid report is skipped
  rather than fatal: the report parsed, so the run is accounted for, and one bad row should
  not discard a long scan.

## Config types match VardrMap's validator exactly

`match_codes` takes a bare status code (`200`) as well as a string or list, because that is
what a JSON caller naturally sends and VardrMap accepts it. `extensions` takes only strings
and lists — an extension is never a number — and VardrMap refuses the same types.

The two validators have to agree on precisely which types pass. A type VardrMap accepts and
this refuses clears queue-time validation and then fails on the operator's machine, which is
the failure mode queue-time validation exists to prevent. Both repos carry the same table
(`test_accepted_types_match_vardrmaps_validator` here, `test_accepted_types_match_the_runners`
there) so the pair cannot drift silently.

## An unreachable target no longer looks like "nothing found"

Found by the opt-in smoke test below, not by any mocked test. For a host that refuses the
connection, ffuf 2.3.0 exits **0** and writes a **valid, empty report** — with `-s`, `-se` and
`-sa` alike, so no flag helps. The handler could not tell "there was nothing there" from "it
could not look", and the job succeeded with no results: the same unknown-versus-nothing confusion
the handler guards against for an *unreadable* report, except that here ffuf itself hides the
difference.

**Fixed with a reachability probe.** Each target gets one GET before any fuzzing; if nothing
answers, the job fails with the reason and sends no fuzzing traffic. Any HTTP response counts as
reachable (404, 403, 500, and redirects, which are not followed); connection errors, timeouts and
a failed TLS handshake does not (an untrusted certificate is fine, see below). It costs one request per target, identified by its User-Agent,
and does not close the window between the probe and the fuzz. Alternatives were an accept-and-
document stance, or parsing ffuf's output, which prints nothing on this failure even without `-s`.
## Scheduled runs

### The probe does not verify TLS, because ffuf does not

An earlier revision of the probe verified certificates, on the stated assumption that ffuf does too.
That was never tested, and it is false: pinned ffuf 2.3.0 scanned a self-signed, an expired and a
hostname-mismatched certificate and found the same paths on each, while the verifying probe rejected
all three. It would have failed jobs on exactly the self-signed hosts a pentest is full of. The probe
now skips verification to match; it sends one GET with a fixed User-Agent and no credentials, cookies
or body, so nothing sensitive is exposed by that. A failed handshake (not speaking TLS, plain HTTP to a
TLS port) is still unreachable.

Pinned by three tests against the real binary, which go red if the old behaviour returns, plus unit
tests against throwaway untrusted-certificate servers (the certificates are generated at test time, so
no private key is committed; `cryptography` is added to the **dev** extra for this).

A schedule queues an ordinary job, so `run ffuf` can recur. `--rate` applies **per
execution**, not across the engagement: each run is a fresh process with its own full
allowance, and nothing aggregates traffic across runs or overlapping jobs. An hourly schedule
means active fuzzing traffic every hour for as long as it exists. `--rate` bounds how hard one
run pushes, not how often runs happen.

## Opt-in smoke test against the real binary

`tests/test_smoke_ffuf.py` runs the **actual pinned ffuf** through the real handler against a
fixture server on `127.0.0.1`. Set `VARDRRUNNER_SMOKE=1`; without it the tests skip, and with
it but no binary available they skip and say how to install it. It checks that ffuf accepts
every flag we pass, that real output is parsed into the records VardrMap reads (calibration
dropping the 404s), that a run with no matches is a valid empty result backed by requests
actually made, that ffuf exits 0 for an unreachable target, and that the handler's probe turns that
into a failed job. Safety is asserted: loopback only,
a request ceiling, a capped rate, a tiny wordlist and a 60-second timeout.

## Known rough edge: preview counts recon rows, not roots

`--limit` and a queued job's `limit` cap **recon rows**, and targets collapse to site roots
*after* that cap. So 100 recon URLs that all live on one host consume the default limit and
fuzz one root. VardrMap's `POST /jobs/preview` has the same shape: it reports the resolved
recon targets, not the roots ffuf will actually fuzz, so for ffuf its `count` is an upper
bound rather than the execution set. Raise `limit`, or use the scope source, when recon is
dense on few hosts. Making preview collapse roots would mean duplicating this normalization
in the backend, which is the kind of drift that produced the type mismatch above, so it is
left for a shared fix rather than a second copy.

## One ffuf run per target

ffuf can fuzz many hosts in a single run through its `-w path:KEYWORD` syntax, and this
does not use it. A Windows wordlist path already contains a colon (`C:\lists\common.txt`),
and ffuf's documentation does not say which colon separates the keyword. Rather than guess
at argv construction for a tool that sends traffic, the handler loops with the canonical
bare `-w <path>` and ffuf's default `FUZZ` keyword, which has no ambiguity. `timeout`
therefore bounds each target rather than the job.

The uploaded records keep ffuf's own key spelling (`input.FUZZ`, `status`, `content-type`),
because VardrMap's `parse_ffuf` already reads exactly those — so the import side needed no
parser change.

## Also in this release

- **`toolchain` accepts an uppercase version flag.** `version_args` was validated against a
  lowercase-only pattern; ffuf's flag is `-V`. The check still admits nothing but a bare
  flag — no separator, value, path or whitespace.
- **`runner.base_url` drops targets that are not web hosts.** Two cases are worth naming
  because both appear in real recon and both survive a naive scheme prefix: a `mailto:` or
  `javascript:` entry parses as userinfo plus a host once `https://` is prepended, and a URL
  carrying credentials would have had them replayed at the target. Both now resolve to
  nothing and are dropped. Found by a test written for the parametrized table, not in
  review.
- `ffuf` is pinned at **2.3.0** for all five platforms, hashes cross-checked against ffuf's
  own `checksums.txt` by `scripts/pin_tools.py`.

## Not changed

Pipelines are untouched: ffuf is active and noisy, so it is not added to `content` (or any
other chain) by default. Queue it deliberately, ideally against hosts httpx has already
confirmed live.

## Tests

`tests/test_ffuf.py` covers config defaults and every rejection (paths, traversals, drive
letters, uppercase, bad extensions, bad statuses, rate bounds, and that no value disables
the rate cap); `base_url` normalization including the `mailto:`/`javascript:`/credential
cases; wordlist resolution (missing, empty, invalid names, traversal); argv construction
including that the wordlist is passed bare with no `:FUZZ` suffix; and the handler —
root collapsing, one run per target, record merging and de-duplication, no-results,
failure propagation, that nothing launches when the wordlist is absent, chunked upload, and
handoff targets. Report integrity has its own set: an absent, non-JSON, wrong-shaped or
`results`-less report fails; a valid empty one succeeds as a real empty result; one bad entry
among good ones is skipped; and a run whose report never appears fails the job rather than
going green. A parametrized table pins the accepted config *types* against VardrMap's. `tests/test_cli.py` asserts the kwargs every ffuf
option produces and that an out-of-range `--rate` never reaches the command.

1196 tests, 95.80% coverage.
