# v0.43.0 — ffuf

**Date:** 2026-10-09

Active content discovery. Stage 2b of the tool sequence ADR 0014 anticipated.
**Pairs with VardrMap v0.40.0**, which makes `ffuf` a queueable job type.

## What it does

```bash
vardrrunner tools install ffuf
mkdir -p ~/.vardrmap/wordlists
cp /usr/share/seclists/Discovery/Web-Content/common.txt ~/.vardrmap/wordlists/common.txt
vardrrunner run ffuf --engagement <id> --from-recon --wordlist common --rate 25
```

ffuf fuzzes each target's **site root** for hidden paths and uploads the hits as recon.
Targets collapse to roots first (`https://a.test/login` and `https://a.test/admin` are one
root), so a recon table with twenty URLs on one host fuzzes that host once.

| Option | |
|---|---|
| `--wordlist <name>` | A name, not a path. Default `common`. |
| `--extensions .php,.bak` | Appended to each word. A bare `php` gains its dot. |
| `--match-codes 200,301,403` | Statuses to keep, or `all`. Default: ffuf's own. |
| `--rate N` | Requests per second, per target. 1–1000, default 50. |

## Wordlists are named, never pathed

A queued job sends a wordlist **name**; the runner resolves it against
`~/.vardrmap/wordlists` on the machine doing the scanning. A path, a traversal, a drive
letter — anything path-shaped — is refused.

This is the point of the design, not an inconvenience. If a job could supply a path, the
backend would be able to name any file the runner can read, and ffuf would read it and
replay its lines at a target: a file-disclosure primitive built out of two features that
are each individually reasonable. The name's shape (`[a-z0-9][a-z0-9_-]*`) admits no
separator, `FfufConfig` refuses anything else at parse time, and `runner.resolve_wordlist`
re-checks the resolved parent before the subprocess starts. A symlink *inside* the
directory is honoured — pointing `common.txt` at a SecLists file is the operator's own
decision on their own machine, and nothing the backend can influence.

No wordlists ship with VardrRunner; their licences and sizes are the operator's choice. A
missing or empty one fails the job with a message naming the file it expected.

## Load is capped, and calibration is not optional

ffuf is the only tool here that puts sustained load on a client's host, so:

- **`-rate` is always passed.** It has a modest default (50/s), a ceiling of 1000, and no
  value that disables it. ffuf's own default is unbounded threads.
- **`-ac` (auto-calibration) is always on.** A host that answers every path with `200`
  would otherwise import thousands of phantom endpoints into the shared recon store, which
  is worse than finding nothing — it is wrong data in an engagement's record.
- **A non-zero exit on any one target fails the job.** Skipping that host quietly would
  report coverage the engagement does not actually have.

## One ffuf run per target

ffuf can fuzz many hosts in a single run through its `-w path:KEYWORD` syntax, and this
does not use it. A Windows wordlist path already contains a colon (`C:\lists\common.txt`),
and ffuf's documentation does not say which colon separates the keyword. Rather than guess
at argv construction for a tool that sends traffic, the handler loops with the canonical
bare `-w <path>` and ffuf's default `FUZZ` keyword, which has no ambiguity. `timeout`
therefore bounds each target rather than the job.

The uploaded records keep ffuf's own key spelling (`input.FUZZ`, `status`, `content-type`),
because VardrMap's `parse_ffuf` already reads exactly those — so the import side needed no
parser change.

## Also in this release

- **`toolchain` accepts an uppercase version flag.** `version_args` was validated against a
  lowercase-only pattern; ffuf's flag is `-V`. The check still admits nothing but a bare
  flag — no separator, value, path or whitespace.
- **`runner.base_url` drops targets that are not web hosts.** Two cases are worth naming
  because both appear in real recon and both survive a naive scheme prefix: a `mailto:` or
  `javascript:` entry parses as userinfo plus a host once `https://` is prepended, and a URL
  carrying credentials would have had them replayed at the target. Both now resolve to
  nothing and are dropped. Found by a test written for the parametrized table, not in
  review.
- `ffuf` is pinned at **2.3.0** for all five platforms, hashes cross-checked against ffuf's
  own `checksums.txt` by `scripts/pin_tools.py`.

## Not changed

Pipelines are untouched: ffuf is active and noisy, so it is not added to `content` (or any
other chain) by default. Queue it deliberately, ideally against hosts httpx has already
confirmed live.

## Tests

`tests/test_ffuf.py` covers config defaults and every rejection (paths, traversals, drive
letters, uppercase, bad extensions, bad statuses, rate bounds, and that no value disables
the rate cap); `base_url` normalization including the `mailto:`/`javascript:`/credential
cases; wordlist resolution (missing, empty, invalid names, traversal); argv construction
including that the wordlist is passed bare with no `:FUZZ` suffix; and the handler —
root collapsing, one run per target, record merging and de-duplication, no-results,
failure propagation, that nothing launches when the wordlist is absent, malformed reports,
chunked upload, and handoff targets. `tests/test_cli.py` asserts the kwargs every ffuf
option produces and that an out-of-range `--rate` never reaches the command.

1196 tests, 95.80% coverage.
